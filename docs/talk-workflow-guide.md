# Talk to Familiar — user and operator guide

The **Talk** page is the conversational way to start work. You describe what you need in ordinary
language, review a structured proposal, and approve it. Approving creates one task and one Planner
session, which an eligible worker then runs on its own.

This guide covers what the workflow does, the guarantees it makes, and how to operate and
troubleshoot it.

---

## The one thing worth knowing

**Nothing runs until you approve it.**

Describing work creates only a conversation, your message, and a proposal. No task exists. No
session exists. No AI has been called. Your project's context is untouched.

Approval is the single action that creates work — and it creates exactly one task and exactly one
Planner session, no matter how many times the button is pressed.

---

## The workflow

```text
Open Talk
    |
    v
Describe the work in ordinary language
    |
    v
Review the proposal: project, title, outcome, Planner role
    |
    v
Revise it if needed  ---------> (still nothing created)
    |
    v
Approve
    |
    v
One Ready task + one Started Planner session
    |
    v
An eligible worker discovers and runs it automatically
```

### 1. Describe the work

Go to **Talk** and write what you need. Keep it to one bounded piece of work — a request becomes
one task, not a project plan.

- Name the project if you can. It makes the proposal unambiguous.
- The first line becomes the proposed task title, so a good first line saves you an edit.
- Up to 4,000 characters.

### 2. Review the proposal

Familiar shows you a structured proposal:

| Field | Where it comes from |
|---|---|
| **Project** | Matched from your request, or left for you to choose |
| **Task title** | The first non-empty line of your request, up to 200 characters |
| **Requested outcome** | Your full request |
| **Session role** | Always Planner — not editable |
| **Observed context revision** | The project's context revision when you reviewed it |

The proposal is generated by fixed rules, not by an AI. That is deliberate: the same request always
produces the same proposal, and you can see exactly why a project was chosen.

**How the project is chosen:**

1. If exactly one active project's complete name appears in your request → that project.
2. If no project name appears and you have only one active project → that project.
3. Otherwise → left unresolved, and you pick it. Familiar never guesses between two projects.

Archived projects are never proposed and cannot be approved.

### 3. Revise if needed

While the proposal is pending you can change the project, title, and requested outcome. The role
stays Planner.

Each revision is recorded as a new message rather than overwriting history, so the conversation
shows how the proposal evolved.

### 4. Approve or reject

- **Approve** creates one Ready task and one Started Planner session, and links the conversation to
  both.
- **Reject** closes the conversation and creates nothing.

Both are final. An approved or rejected conversation cannot be reopened — describe new work
instead.

### 5. The worker takes over

From approval onward, nothing is conversational. The session is an ordinary Planner session on the
ordinary work queue, and Sprint 07's worker discovers, claims and executes it exactly as it does
for a session you started by hand.

The conversation page shows the task and session status for convenience. It is display only — the
conversation never decides what may run.

---

## Guarantees

| Guarantee | What it means |
|---|---|
| No work before approval | Intake and revision write only conversation records |
| No AI before approval | The proposal is deterministic; the Planner session is the first provider call |
| Exactly one task and session | Concurrent or repeated approvals produce one task and one session |
| All-or-nothing approval | A failure leaves no task, no session, and no context-revision drift |
| Reviewed context only | If project context changed since you reviewed, approval stops |
| Planner only | No Implementer or Reviewer session ever starts automatically |
| Works without JavaScript | Plain forms, POST/redirect/GET, standard antiforgery |

## Messages you may see

### "The project's context changed since you reviewed this proposal."

Something added context, changed a task status, or completed a session on that project after you
loaded the page. Approval stopped on purpose — the plan the Planner receives would not be the one
you reviewed.

**What to do:** press **Refresh project context**, re-read the proposal, then approve. Refreshing
records the new revision and invalidates any approve button rendered earlier, which is what forces
the second look.

### "The proposal changed after this page was loaded."

Someone (or another tab) revised or acted on this proposal. Your submission was not applied and
nothing was overwritten.

**What to do:** reload the page and review the current proposal.

### "Another request changed this conversation at the same time."

Two actions raced. Nothing was created by the losing one.

**What to do:** reload and check the current state — the other action may have already done what
you wanted.

### "This conversation was already approved."

A duplicate submission, usually a double-click or a refreshed POST. This is not an error: the page
still links to the single task and session the first approval created.

### "Select the project this work belongs to."

Your request was ambiguous — either several project names appeared, or none did and you have more
than one active project. Choose the project in the revise form.

## Operator notes

### Nothing new to deploy

Sprint 08 adds no service, port, endpoint, credential or worker configuration. The runner contract
version is unchanged. An existing, already-configured worker picks up approved sessions with no
changes at all.

### The migration

One additive migration, `ConversationalWorkIntake`, creates three tables:

- `Conversations` — lifecycle state, timestamps, and links to approved work
- `ConversationMessages` — append-only visible messages, ordered per conversation
- `WorkProposals` — the editable proposal and its concurrency token

It creates no columns on, and changes no data in, any existing table. Applying it is a normal
`dotnet ef database update` or an ordinary application start, which migrates automatically.

Rolling back is a table drop and loses conversation history only — approved tasks and sessions are
ordinary rows in the existing tables and are unaffected.

### What is never stored

Conversation tables hold visible text and structured proposal fields only. No credentials, no
environment values, no repository paths, no worker mappings, no machine names, no provider
transcripts, and no hidden model reasoning. Repository mappings remain entirely worker-side, as
ADR-0008 requires.

### Deleting a conversation

Deleting a conversation cascades to its messages and proposal. It **cannot** delete an approved
task or session — those links are restricted, so approved work survives the conversation that
requested it.

### Verifying the boundary yourself

Describe work on the Talk page, then check the database before approving:

```sql
SELECT COUNT(*) FROM Tasks;          -- unchanged
SELECT COUNT(*) FROM AgentSessions;  -- unchanged
SELECT ContextRevision FROM Projects WHERE Id = '<project>';  -- unchanged
```

After approving, exactly one task and one session appear, and the project's context revision
advances by exactly two — one for task creation, one for the session start, the same as doing it by
hand.
